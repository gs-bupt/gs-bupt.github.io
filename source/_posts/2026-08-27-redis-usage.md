## 为什么需要 Redis

Redis 基于内存提供低延迟读写，适合承载访问频繁、允许一定缓存一致性延迟的数据。数据库仍然是主要事实来源，Redis 更适合作为缓存、计数器、排行榜、会话存储或轻量级队列。

Redis 的命令执行核心长期以来以单线程为主，从而避免了大量锁竞争和线程上下文切换；Redis 6 以后也支持 I/O 线程，持久化和网络等工作还可能由后台线程完成。因此“Redis 是单线程”应理解为命令执行模型，而不是所有工作都只有一个线程。

## 数据结构与常见场景

| 类型 | 典型用途 | 注意事项 |
| --- | --- | --- |
| String | 缓存、计数器、分布式锁 | 配合 `EXPIRE`，控制大小 |
| Hash | 用户资料、对象字段、计数集合 | 避免单个 Hash 无限增长 |
| List | 简单队列、时间线 | 高可靠队列应考虑 Streams 或专业消息系统 |
| Set | 去重、集合运算 | 注意成员数量和内存 |
| Sorted Set | 排行榜、延迟队列 | 关注元素数量和命令复杂度 |

Redis 支持 RDB 和 AOF 持久化。缓存场景可以接受部分数据丢失，但订单、支付等核心数据不能只依赖 Redis。

## 六个常见应用

### 连续签到

可以使用 `user:sign:{userId}` 保存签到状态或计数，并把过期时间设置到下一个结算周期。过期时间要按业务时区计算，不能简单地固定为 24 小时。

### 消息通知

`LPUSH`/`BRPOP` 可以实现简单队列，但需要处理消费者崩溃、重复消费和消息确认。对可靠投递、重试和消费组有要求时，应使用 Redis Streams 或消息队列。

### 计数器

使用 `INCR`、`HINCRBY` 维护点赞、浏览等计数。高并发下 Redis 操作是原子的，但异步回写数据库时要设计补偿和对账机制。

### 排行榜

使用 `ZINCRBY leaderboard score userId` 更新分数，再通过 `ZREVRANGE` 获取排名。分数相同时应明确业务上的排序规则。

### 限流

固定窗口可以用 `INCR` 配合 `EXPIRE`，滑动窗口则需要 Sorted Set 或令牌桶算法。限流 key 应包含用户、接口和时间窗口，避免不同业务相互影响。

### 分布式锁

不要只使用 `SETNX`，应使用带随机值和过期时间的原子命令：

```redis
SET lock:order:123 request-id NX PX 10000
```

释放锁时必须校验 value 确实属于当前请求，再通过 Lua 脚本删除，避免误删其他请求持有的锁。锁的租约、续期和业务执行时间也要一起设计。

## 大 Key 与热 Key

“大 Key”没有适用于所有业务的统一阈值，常见经验是单字符串达到几十 KB，或集合成员数、总大小明显偏大。它会增加网络传输、序列化、删除和主从复制成本。可以通过拆分、压缩、分页和冷热分离降低影响；删除大 Key 时优先考虑 `UNLINK`，并在压测后评估收益。

“热 Key”是访问集中导致单个 Redis 实例负载不均衡。常见方案包括：

1. 在应用侧增加带过期时间的本地缓存；
2. 将热点数据复制到多个 key，读取时分散请求；
3. 使用合理的分片、代理或集群架构。

复制热点 key 会增加写入和一致性成本，只适合读多写少且能接受短暂延迟的场景。

## 慢查询与缓存稳定性

避免一次批量处理过多 key、对超大 Sorted Set 做昂贵操作，以及在请求线程中同步删除大对象。开启慢查询日志并结合命令复杂度、网络耗时和实例 CPU 一起分析。

缓存穿透是请求不存在的数据，可以缓存短 TTL 的空值或使用布隆过滤器；缓存击穿是单个热点 key 失效，可以使用互斥重建、逻辑过期或预热；缓存雪崩是大量 key 同时失效，应使用随机 TTL、分批过期、限流和降级。

## 小结

Redis 的性能来自简单的数据模型和内存访问，但稳定性取决于 key 设计、过期策略、容量治理、持久化和故障演练。上线前应明确数据是否可丢失、缓存与数据库谁是事实来源，以及异常时的降级路径。
